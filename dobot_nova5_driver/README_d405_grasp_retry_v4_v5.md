# V4 / V5 D405 抓取重试优化（2026-10-19）

针对 `continuous-18/19/20` 日志中的两次接近后退回、第三次才夹取：

- 重试曾直接接收 `age=2.618s` 的旧停盘跟踪缓存，同时重新启动 D405，导致机器人离开初始位后视觉才按固定 ROI 重识别。
- 悬停校验缺少新鲜帧时原来立即失败，没有给短暂跟踪中断留出恢复时间。

## 修改后的行为

1. 启动预跟踪、停盘重识别和显式视觉请求都设置新的采集时间边界。视觉处理循环实际开始采集后，通过现有 `/d405_vision_result` 话题发送 `acquisition_started:<request_epoch>:<capture_epoch>`。这类消息不计入检测成功、失败或空盘确认。
2. 驱动等待采集确认，并拒绝前一轮及采集边界之前的图像结果；相机端也禁止旧采集帧进入新的稳定帧组合。推理过程中到达的新请求不会被旧循环清除触发标志的操作吞掉。
3. 停盘预跟踪目标同时检查接收时间、图像采集时间和本轮计数，继续要求稳定样本、CLEAR 状态及尺寸合法。
4. 确认安全悬停高度后，如缺少合格跟踪帧，最多等待 0.60 秒。已有合格帧立即继续；等待期间不由驱动触发 YOLO 或发送运动指令，安全停止仍可打断。超时仍回初始位重试。
5. 固定 ROI 选择范围保持原样。通过先在初始位完成本轮重识别，避免旧缓存让机器人先行离开，再异步重置 SAM2。持续遮挡、真实障碍或目标身份变化仍可能触发重试。

## 参数和使用

| 参数 | 默认值 | 用途 |
| --- | --- | --- |
| `pregrasp_fresh_wait_timeout_s` | `0.60` 秒 | 悬停缺帧等待上限，范围 0–2 秒；0 表示不等待 |
| `pregrasp_pose_max_age_s` | `0.65` 秒 | 新鲜度限制，停盘跟踪与悬停检查同时校验接收、采集时间 |

两个版本的 D435 launch 均暴露等待参数，例如在原有启动命令末尾追加：

```bash
pregrasp_fresh_wait_timeout_s:=0.6
```

驱动、对应版本 D405 视觉脚本应配套重启。已运行的进程不会自动加载这些修改。启动入口继续使用各自 V4 / V5 的源码视觉脚本；驱动及 launch 的安装副本同步更新。

日志新增 `capture_age`，悬停等待时会出现 `D405 tracking gap at safe hover`，恢复后出现 `D405 fresh tracking recovered at safe hover`。失败信息同时列出最近接收年龄和采集年龄，便于区分旧图像与无回包。
